# aalint 2.4.1-test2 说明

这一版不是继续扩张 lint，而是使用 `aardio.zip` 中保留的官方源码重新校正 aalint 的职责边界。

## 从官方源码确认的关键事实

- `config/SYS.THEME` 明确定义了双引号、反引号、单引号、可变星号 `/*...*/` 以及模板 `?> ... <?` 的 WholeText/escape 行为，因此 aalint 的代码遮罩不能按 C/JS lexer 处理。
- `config/intellisense/kernel.txt` 明确说明：
  - `loadcode()` 是编译语法的官方真值来源；
  - `call()` 捕获异常但默认不触发 `global.onError`；`callex()` 才会按参数触发；
  - `global.onError(err,over)` 在 `!over` 时可附加 `debug.traceback`；
  - `fiber.create(func, appBaseDir)` 会同时改变 AppRoot 与用户库目录；
  - 如果该 fiber 内创建窗口后因异常停止，残留窗口回调可能出现 `cannot resume fiber`。
- `lib/ide/debug.aardio` 包含 IDE 官方错误字段解析和 aardio 专属提示逻辑，aalint 的错误输出应尽量贴近这里，而不是重新发明一套异常分类。
- `lib/console/_.aardio` 显示 `console.writeText()` 绕过 `io.stdout`，`console.error()` 使用 `console.stderr/io.stderr`；因此完整 capture 需要同时覆盖两条路径。
- `lib/win/ui/_.aardio` 显示 `oncommand` 最终由父窗口 `WM_COMMAND` 分发；标准 Button 的 `BM_CLICK` 和直接 `WM_COMMAND` 不应视为同一种 flow 动作。
- `io.libpath()` 是官方库解析入口。手工拼 `lib\foo.aardio` / `lib\foo\_.aardio` 既重复又可能与实际搜索规则不一致。
- 官方源码本身大量合法使用单 `=` 条件、`table.isArray()`、局部变量遮蔽以及可能返回 falsy 的三元真分支；这些规则不应默认干扰 Agent。

## 本版修改

1. 模板原文进入 lexical masker：仅当源码首个非空白内容以 `<?` 或 `?>` 开始时启用模板模式，避免普通源码偶然出现 `?>` 被误切换；HTML/批处理/IDL 原文不会被 lint/import/snapshot 当成 aardio 代码。
2. snapshot 注入仅在真实 CODE 区域定位 `win.loopMessage`。
3. 默认 lint 收敛；争议/启发式规则只在 `--lint-all` 中启用。
4. imports 改用 `io.libpath()`，并识别 `import global`。
5. API 查询可通过 `process.aardio.getDir()` 找已安装的标准库源码。
6. capture 增加 stderr/console.error。
7. UI flow 增加更贴近 win.ui 消息模型的 `command`/message/assert 动作。
8. onError 返回 null，避免 aalint 已记录错误后再由默认处理器重复显示。

## 官方源码样本反查

对 `aardio.zip` 中可直接按文本读取的 711 个 `.aardio` 文件做静态代码区遮罩反查（跳过 1 个含 NUL/二进制数据的特殊 `.aardio` 文件）：

- 默认 `foreign-idiom`：0 命中；
- 默认 `thread-invoke-call` 的危险形态 `thread.invoke(fn())`：0 命中。

这不是编译器验证，只用于检查默认 lint 是否会直接污染官方源码样本。真正语法结论仍以 aardio 编译器为准。

## 建议优先测试

### 1. 模板文件

构造包含下列内容的模板 `.aardio`：

```aardio
?>
<script>
// 这些都不能被 aalint 当 aardio 代码
import fake.not.exists;
var x = ()=>{};
win.loopMessage();
</script>
<?
import console;
console.log('ok');
```

验证 `--lint`、`--imports`、snapshot 注入都只处理 `<?` 后的 aardio 代码。

### 2. import 解析

在真实 `.aproj` 工程子目录运行：

```text
aalint --imports src\test.aardio
```

覆盖工程 `lib`、标准库、目录库、文件库以及 `import global`。

### 3. stderr/capture

```aardio
import console;
console.error('console-error');
io.stderr.write('stderr\r\n');
console.writeText('writeText');
```

验证 `--run --capture` 能拿到三种输出，并且下一文件运行时 console/io 句柄已恢复。

### 4. UI 回调异常

优先：

```text
aalint --run-isolated --ui-flow flow.json --timeout 8 main.aardio
```

让按钮 `oncommand` 中故意访问 null 字段，确认能得到失败与 traceback，而不是只因为主文件 `loadcode()` PASS 就结束。

### 5. snapshot 假标记

在真实 `win.loopMessage()` 前放置：

- 双引号/单引号/反引号中的 `win.loopMessage();`
- `/***** ... *****/` 中的标记
- `?> ... <?` 模板原文中的标记

确认 `--setup` / snapshot 注入落在真正的消息循环之前。

## 暂未改动的风险

### `--lib`

当前实现为了合并项目 lib 与自定义 lib，会把 fiber AppRoot 指向临时目录。官方内核明确说明 AppRoot 与用户库目录在 `fiber.create(..., appBaseDir)` 中一起变化，因此这可能改变 `/res`、`/config` 等工程相对路径语义。

在没有找到官方“只追加一个用户库搜索目录、但保持 AppRoot 不变”的公开接口以前，本版不做猜测式重构。

### UI + fiber

`--run` 仍依赖 AppRoot fiber。官方内核明确警告 UI 所在 fiber 异常停止后残留窗口回调可能 `cannot resume fiber`。因此 UI 行为验证当前最稳妥的模式仍是 `--run-isolated --ui-flow`。

### isolated 实时输出

父进程目前仍周期性读取 capture 文件，尚未改成基于 `process.popen.stdOut/stdErr` 的完整双向协议。官方 `process.popen` 已提供这套能力，后续值得重构，但 test2 不同时改运行协议以降低回归风险。

### `--api`

仍然是轻量源码签名提取，不等同于 IDE 全部智能提示数据库。官方 `ide.doc` / intellisense 数据值得后续进一步利用。
